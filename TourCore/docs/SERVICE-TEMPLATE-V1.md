# Шаблон сервиса TourCore — версия 1

**Статус:** первая зафиксированная версия архитектурного шаблона.  
**Дата оценки:** 12 октября 2026 года.  
**Объект оценки:** текущий `TourCore.Admin.Api` и связанные проекты решения.

## Назначение

Документ превращает исходный список из 12 рекомендаций в проверяемые требования
к новым сервисам TourCore. Он одновременно фиксирует исходное состояние текущего
сервиса и показывает, какие части шаблона ещё предстоит реализовать.

Это также рабочая инструкция для Codex: когда пользователь описывает новый сервис,
Codex должен спроектировать, реализовать и проверить его по этому шаблону. Отдельно
ссылаться на все 12 пунктов в каждом запросе не требуется — достаточно описать
назначение сервиса и его бизнес-сценарии.

Шаблон не требует добавлять технологию «на всякий случай». PostgreSQL, MongoDB,
gRPC, брокер сообщений или распределённый кеш подключаются только при наличии
сценария, который оправдывает их эксплуатационную стоимость. Обязательны границы,
позволяющие подключить нужную реализацию без переноса бизнес-логики.

## Как применять шаблон к новому сервису

Получив описание нового сервиса, Codex должен:

1. Выделить ответственность сервиса, его владельца данных, входные сценарии и
   границы с другими контекстами.
2. Сопоставить задачу со всеми 12 разделами этого шаблона и определить, какие
   возможности обязательны, какие не применяются, а какие следует отложить.
3. Зафиксировать существенные допущения. Запрашивать уточнение только тогда, когда
   выбор заметно меняет бизнес-поведение, модель данных, публичный контракт или
   эксплуатационные свойства сервиса.
4. Создать слои Domain, Application, Contracts, Infrastructure и host в объёме,
   оправданном задачей. Пустые проекты и абстракции «на будущее» не создаются.
5. По умолчанию применить минимальный профиль нового сервиса из этого документа.
6. Добавлять кеш, дополнительные базы, gRPC и брокер только при наличии сценария;
   при добавлении выполнить критерии соответствующего раздела полностью.
7. Реализовать тесты, контейнеризацию, health checks, конфигурацию, безопасность и
   наблюдаемость как часть сервиса, а не как необязательную последующую работу.
8. Обновить документацию сервиса: назначение, API/сообщения, данные, зависимости,
   локальный запуск, миграции и осознанные отклонения от шаблона.
9. Собрать решение и выполнить релевантные unit, integration, architecture и smoke
   tests. Непроверенные части явно перечислить в результате работы.
10. В итоговом отчёте дать матрицу соответствия 12 пунктам со статусами
    «соответствует», «частично», «не соответствует» или «не применяется».

Если пользователь явно задаёт технологию или архитектурное решение, оно имеет
приоритет для данного сервиса. Codex должен сообщить о существенном риске или
противоречии с шаблоном, но не должен молча подменять поставленное требование.

## Шкала оценки

- **Соответствует** — требование реализовано и пригодно для повторного использования;
- **Частично соответствует** — правильная граница уже есть, но реализация неполна
  или покрывает только текущий сценарий;
- **Не соответствует** — необходимой границы или реализации пока нет;
- **Не применяется** — возможность осознанно не нужна данному сервису.

## 1. Host, конфигурация, логирование и фоновые операции

### Смысл

`Program.cs` должен быть composition root, а не местом бизнес-логики. Он собирает
конфигурацию, DI, middleware, endpoints, health checks и наблюдаемость. Настройки
берутся из стандартной цепочки ASP.NET Core: `appsettings.json`, environment-specific
JSON, environment variables, user secrets и аргументы командной строки.

Логи должны быть структурированными и коррелироваться с traces. Метрики, traces и
логи экспортируются через OpenTelemetry. Prometheus — один из возможных backend
метрик, а не обязательная зависимость бизнес-кода. Периодические операции, прогрев
или обновление кеша выполняются через `BackgroundService`/`IHostedService`, получают
собственный DI scope, поддерживают cancellation и не запускаются через бесконтрольный
`Task.Run` рядом с HTTP-логикой.

### Критерии шаблона

- `Program.cs` содержит только сборку host и вызовы тематических registration methods;
- параметры имеют типизированные Options с validation on start;
- используются структурированные логи без секретов и персональных данных;
- запрос можно связать по `TraceId` между логом, trace и исходящим вызовом;
- есть liveness/readiness checks для обязательных зависимостей;
- телеметрия экспортируется по OTLP и не связывает приложение с конкретным backend;
- фоновые операции реализованы как управляемые workers с graceful shutdown,
  обработкой ошибок и наблюдаемостью.

### TourCore сейчас — частично соответствует

`TourCore.Admin.Api` уже использует JSON console logging, trace/span identifiers,
OpenTelemetry для ASP.NET Core, `HttpClient`, EF Core и runtime metrics, OTLP exporter,
JSON health endpoints и Prometheus через OTel Collector. Регистрация вынесена в
`AddTourCoreObservability()` и другие extension methods. `CreateBuilder` обеспечивает
стандартную загрузку JSON и environment configuration.

Не хватает общего reusable-модуля host defaults и типизированной валидации всех
настроек. `TourCore.Identity.Api` пишет JSON-логи, но не подключён к общей
OpenTelemetry-конфигурации. Управляемых фоновых workers пока нет; это допустимо,
пока нет фонового сценария, но шаблон для них ещё не подтверждён кодом.

## 2. Аутентификация и авторизация

### Смысл

Сервис проверяет удостоверение вызывающего субъекта и принимает решение о доступе
через policies/permissions. Выдача токенов и хранение пользователей не должны
дублироваться в каждом бизнес-сервисе.

### Критерии шаблона

- API является JWT/OIDC Resource Server;
- authorization строится на policies, а не на проверках ролей внутри бизнес-логики;
- health endpoints и остальные anonymous endpoints перечислены явно;
- production использует отдельный IAM/Identity Provider;
- issuer, audience, HTTPS metadata и keys валидируются при старте;
- service-to-service identity и ротация ключей предусмотрены до межсервисного запуска.

### TourCore сейчас — соответствует для первого среза

`TourCore.Admin.Api` проверяет JWT и применяет централизованные policies. Отдельный
`TourCore.Identity.Api` выдаёт локальные токены. Эта реализация подходит для
разработки и первого вертикального среза. Для production ещё нужны внешний IAM либо
полноценный Identity Service, JWKS/ротация ключей, refresh/revocation и машинные
клиенты. Подробности закреплены в `AUTHORIZATION.md`.

## 3. Кеширование

### Смысл

In-memory, distributed Redis, snapshot/index и HTTP-кеш решают разные задачи и не
являются взаимозаменяемыми. Бизнес-логика зависит от порта кеша, а не от конкретного
клиента. Кеш всегда считается производным и восстанавливаемым хранилищем.

### Критерии шаблона

- для каждого кеша описаны владелец, ключи, TTL, размер, invalidation и поведение
  при недоступности;
- явно выбрана модель cache-aside, write-through или публикации snapshot;
- ключ содержит namespace и версию схемы/данных там, где это необходимо;
- реализация заменяется через DI;
- потеря кеша не приводит к потере авторитетных бизнес-данных;
- проверены stampede, stale data, serialization compatibility и multi-instance режим.

### TourCore сейчас — частично соответствует

В Application существуют `ICatalogCacheProvider`, `ICatalogCacheUpdater` и
`ICatalogCacheInvalidator`, а host подключает `NoCacheCatalogServices`. Это сохраняет
бизнес-логику независимой от технологии, но фактического кеша, TTL, versioning,
защиты от stampede и тестов распределённого режима пока нет. Общие принципы уже
зафиксированы в `DATA-ARCHITECTURE.md`.

## 4. Несколько контекстов и хранилищ

### Смысл

Один host при обоснованной необходимости может использовать несколько независимых
контекстов: command/write store, read model, legacy source или document store. Это
не означает общую транзакцию между ними и не требует от каждой доменной сущности
одновременно поддерживать PostgreSQL, SQL Server и MongoDB.

Domain не знает об ORM и СУБД. Application задаёт порты чтения/записи. Каждый
адаптер инфраструктуры преобразует собственную persistence model в доменную модель.
Между разными базами используются стабильные ID и сообщения, а не cross-database
JOIN и физические foreign keys.

### Критерии шаблона

- каждый контекст имеет отдельные connection settings, registration method,
  migrations и health check;
- read и write interfaces разделены, если у них разные модели или SLA;
- нет общей ACID-транзакции между независимыми источниками;
- retry и transaction policy задаются для конкретного provider;
- SQL Server/MongoDB добавляются отдельным adapter project только по реальной задаче;
- переключение provider не требует изменения Domain и основной бизнес-логики.

### TourCore сейчас — частично соответствует

Domain/Application отделены от EF Core, а документация предусматривает отдельные
контексты и базы. Фактически host подключает один `TourCoreDbContext` через общий
`AddPostgresInfrastructure`. PostgreSQL является целевым transactional store;
SQL Server рассматривается только как источник миграции, MongoDB не используется.
Одновременная работа нескольких контекстов пока не доказана реализацией и тестом.

## 5. Собственная инфраструктура каждого контекста

### Смысл

Контекст владеет своим persistence adapter: реализациями repository ports,
mapping, `DbContext`/client, migrations и регистрацией DI. Это не позволяет одному
«универсальному репозиторию» или контексту превратиться в скрытую общую базу системы.

### Критерии шаблона

- у контекста есть явно названный infrastructure module и registration method;
- интерфейсы репозиториев находятся в Application соответствующего контекста;
- реализации и ORM-типы находятся только в Infrastructure;
- host подключает только нужные контексты;
- migrations и integration tests принадлежат своему контексту;
- транзакция/Unit of Work не пересекает границу независимых контекстов.

### TourCore сейчас — частично соответствует

Интерфейсы репозиториев отделены от EF, реализации находятся в
`TourCore.Infrastructure.Postgres`. Однако один `TourCoreDbContext`, одна сборка
миграций и reflection-регистрация всех найденных репозиториев пока объединяют
Catalog и Product сильнее целевого шаблона. Требуется перейти к явным методам вида
`AddPostgresCatalogInfrastructure()` и отдельным контекстам/миграциям.

## 6. Модуль бизнес-логики

### Смысл

Бизнес-правила живут в Domain и Application, внешние операции представлены
интерфейсами, а конкретные adapters выбираются composition root через DI. HTTP,
EF Core, брокер и кеш не должны определять устройство бизнес-логики.

### Критерии шаблона

- Domain содержит инварианты и не зависит от host/infrastructure;
- Application содержит use cases, ports, orchestration и validation;
- Contracts содержит внешний стабильный API/события;
- Infrastructure реализует ports;
- реализации заменяются DI и тестируются без запуска внешней инфраструктуры.

### TourCore сейчас — соответствует

Решение разделено на Domain, Application, Contracts, Infrastructure и hosts.
Handlers и validators резолвятся через Microsoft DI. `Directory.Build.targets`
контролирует запрещённые project references. Остаточный риск — зависимости Product
от Catalog-проектов; их следует сокращать до стабильных контрактов и ID по мере
физического разделения контекстов.

## 7. DI-контейнер

### Смысл

Базовый контейнер — встроенный Microsoft.Extensions.DependencyInjection. Сторонний
контейнер добавляется только при наличии подтверждённой функции, которой нет в MS DI,
а не ради привычного способа регистрации.

### Критерии шаблона

- registrations сгруппированы по модулю и вызываются из composition root;
- lifetime соответствует зависимости (`Singleton`, `Scoped`, `Transient`);
- singleton не удерживает scoped service;
- при старте проверяются критичные registrations и Options;
- service locator и получение зависимостей из глобального provider запрещены в логике.

### TourCore сейчас — соответствует

Используется Microsoft DI; регистрации вынесены в extension methods. Handler и
repository implementations обнаруживаются reflection и проверяются на единственность.
Для шаблона новых сервисов предпочтительны явные или source-generated registrations,
если reflection начнёт скрывать состав модуля или увеличит startup cost.

## 8. gRPC-коннекторы «источник/приёмник»

### Смысл

Если сервису нужен синхронный внутренний RPC, transport contract описывается в
версионируемом `.proto`. Server adapter переводит запрос в Application command/query,
client adapter скрывает generated client за Application port. Доменные типы не
экспортируются напрямую как transport schema.

### Критерии шаблона

- `.proto` находится в отдельном Contracts/GrpcContracts module;
- package, service и messages версионируются;
- заданы deadline, cancellation, retry только для безопасных операций и status mapping;
- настроены authentication, TLS и telemetry propagation;
- breaking compatibility проверяется в CI;
- gRPC добавляется только при реальном синхронном межсервисном сценарии.

### TourCore сейчас — не соответствует

В решении нет gRPC packages, `.proto`, server endpoints или client adapters. Это не
мешает текущему HTTP Admin API, но reusable gRPC-модуль шаблона ещё не создан.

## 9. Очередь сообщений

### Смысл

Брокер (RabbitMQ, Kafka, Azure Service Bus или другой) нужен для асинхронной
доставки событий и команд. Application публикует логическое сообщение через порт,
а adapter реализует конкретный транспорт. «Ровно один раз» не предполагается:
consumers должны быть идемпотентными.

### Критерии шаблона

- сообщения находятся в версионируемом Contracts module;
- публикация бизнес-факта согласована с БД через transactional outbox;
- приём использует inbox/deduplication и идемпотентный handler;
- определены retry с backoff, dead-letter queue, ordering и poison-message policy;
- trace context/correlation и метрики проходят через producer/consumer;
- локальная инфраструктура и integration test доступны в Compose/Testcontainers.

### TourCore сейчас — не соответствует

Брокер, transport adapter, outbox/inbox и consumers отсутствуют. Документация
описывает будущие события и компенсации, но runtime-контур ещё не реализован.
Выбор конкретного брокера следует делать вместе с первым межсервисным сценарием.

## 10. Тесты каждого сервиса

### Смысл

Каждый deployable host и бизнес-контекст владеет тестовой пирамидой. Наличие общего
тестового проекта не заменяет проверку собственного composition root, контрактов,
persistence adapter и критичных бизнес-сценариев.

### Критерии шаблона

- Domain/Application имеют быстрые unit tests;
- persistence, broker и cache adapters имеют integration tests с реальной технологией;
- API/gRPC имеет contract/component tests, включая auth и ошибки;
- есть smoke test composition root и migrations;
- архитектурные tests проверяют разрешённые зависимости;
- тесты входят в обязательный CI gate, а flaky tests не считаются нормой.

### TourCore сейчас — частично соответствует

Есть `TourCore.Application.Tests`, `TourCore.Catalog.UnitTests` и
`TourCore.Catalog.IntegrationTests`; сборка также контролирует часть архитектурных
зависимостей. Отдельного полного набора для Admin API, Identity, Product и Search,
contract tests и проверки нескольких persistence contexts пока нет.

## 11. Docker и локальное окружение

### Смысл

Сервис должен одинаково собираться и запускаться локально и в CI. Образ остаётся
минимальным, запускается не от root, имеет health check и не содержит секретов.
Compose поднимает сервис и только необходимые локальные зависимости.

### Критерии шаблона

- используется reproducible multi-stage build с pinned major/runtime version;
- process корректно завершает работу по сигналу;
- configuration передаётся environment variables/secrets;
- migrations выполняются отдельным шагом, а не конкурентно каждым API instance;
- Compose содержит health checks и `depends_on` по готовности;
- `.dockerignore`, resource limits и production hardening проверяются отдельно.

### TourCore сейчас — соответствует

Есть отдельные Dockerfiles для Admin API и Identity, `compose.yaml` с PostgreSQL,
одноразовым migrator, Identity, API и OTel Collector, health checks и volume.
Миграции отделены от запуска API. Перед production остаётся проверить non-root user,
image scanning, resource limits, secrets provider и orchestration manifests.

## 12. Отдельные модули контрактов и слабая связанность

### Смысл

Во внешний Contracts module выносятся DTO публичного API, integration events,
commands/messages удалённого взаимодействия и другие стабильные схемы, которыми
пользуются независимые сборки или сервисы. Он не должен ссылаться на Domain,
Infrastructure или host.

Не каждый интерфейс является внешним контрактом. Repository ports, cache ports и
интерфейсы внутренних use cases принадлежат Application: перенос таких интерфейсов
в публичный Contracts module, наоборот, раскрывает внутреннее устройство сервиса и
усиливает связанность.

### Критерии шаблона

- каждый самостоятельный контекст имеет небольшой `<Context>.Contracts`;
- Contracts не содержит EF entities и бизнес-реализаций;
- transport contracts версионируются и проходят compatibility tests;
- другие сервисы не ссылаются на чужие Domain/Application assemblies;
- внутренние ports остаются в Application и реализуются Infrastructure;
- общий Shared не превращается в склад предметных типов.

### TourCore сейчас — частично соответствует

У Catalog, Product и Search существуют отдельные Contracts-проекты, а зависимости
частично контролируются при сборке. Одновременно остаются старые общие
`TourCore.Contracts`/`TourCore.Application`/`TourCore.Domain`, а Product напрямую
ссылается на Catalog Application и Domain. Следующий шаг — завершить перенос по
контекстам и оставить межконтекстные зависимости только через устойчивые контракты,
ID и события.

## Минимальный профиль нового сервиса

Новый сервис обязан начинаться не со всех технологий, а с минимального профиля:

1. Host/composition root, типизированная конфигурация и health checks.
2. OpenTelemetry traces, metrics и structured logs с correlation.
3. Domain/Application/Contracts/Infrastructure с контролем зависимостей.
4. Microsoft DI и явная регистрация модулей.
5. JWT/OIDC Resource Server и policy-based authorization, если API не является
   полностью внутренним anonymous endpoint.
6. Unit tests, integration test выбранного adapter и smoke test host.
7. Dockerfile и локальный Compose-профиль.

Кеш, дополнительный `DbContext`, MongoDB, gRPC и брокер добавляются как capability
packages при появлении соответствующего сценария и должны выполнять критерии своих
разделов выше.

## Версионирование шаблона

- Изменение формулировок и примеров без смены требований выпускается как `v1.x`.
- Добавление или удаление обязательного требования выпускается как новая major-версия.
- Каждый новый сервис указывает, по какой версии шаблона он создан, и перечисляет
  осознанные исключения в своём README/ADR.
- Следующая оценка TourCore должна обновлять статусы в этом документе либо создавать
  отдельный assessment, сохраняя эту версию как исходный baseline.
