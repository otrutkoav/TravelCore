# Карта модулей TourCore

## Core

Core — предметный фундамент TourCore, а не синоним Admin. Без его сущностей остальные модули не имеют самостоятельного смысла.

Физические проекты Core:

```text
TourCore.Domain
TourCore.Contracts
TourCore.Application
```

Текущий состав Core:

- география: страны, регионы, города, курорты;
- базовые гостиничные сущности: отели, категории, типы размещения, комнат и питания;
- транспортные справочники и базовые маршруты: авиа, автобус, железная дорога, трансферы и схемы мест;
- базовые финансовые справочники: валюты и курсы;
- общие для предметного ядра Application-сценарии и абстракции хранения.

`TourCore.Admin.Api.*` управляет Core. Admin не получает собственные Domain/Application/Contracts, пока в нём не появится самостоятельная бизнес-модель, не относящаяся к Core.

Core не может ссылаться на Search, Booking, Quotas, Pricing и другие внешние по отношению к нему модули.

## Shared

`TourCore.Shared` — минимальный технический фундамент:

- базовые примитивы сущностей и результатов;
- handler-интерфейсы;
- стандартные ошибки и их API-представление;
- технические value objects без принадлежности к бизнес-модулю.

В Shared запрещены отели, цены, бронирования, квоты, поисковые модели, внешние DTO, EF/SQL и конфигурация host'ов.

## Реализованные модули

### Search

```text
TourCore.Search.Contracts
TourCore.Search.Application
TourCore.Search.Api.Legacy
```

Ответственность:

- контракт поискового запроса и результата;
- валидация параметров поиска;
- формирование кандидатов тура;
- чтение данных через `ITourSearchDataSource`.

Текущий EF6/SQL Server источник находится в общем `TourCore.Infrastructure.SqlServer/Search`. Это пробная реализация вертикального среза. Публичный API и Application не должны зависеть от способа получения данных.

## Планируемые модули

Названия предварительные и уточняются при начале реализации.

### SearchCache / SearchIndex

- отдельный Service-host;
- построение денормализованных поисковых snapshot'ов;
- полное и частичное обновление;
- атомарная публикация версии кеша;
- Search только читает опубликованные данные и не перестраивает их.

### ActualFilters

- расчёт доступных направлений, дат, продолжительностей и других фильтров;
- производная пересоздаваемая модель, а не источник истины;
- отдельный API/Service-host при необходимости независимого обновления и масштабирования.

### HotelPricing, AviaPricing, OtherPricing

- отдельные правила и источники цен;
- независимые базы из-за разной структуры, нагрузки и жизненного цикла;
- цены не входят в Core и не должны храниться в Search как источник истины.

### Booking

- жизненный цикл заявки;
- состав тура и туристы;
- состояния подтверждения, отмены и оплаты;
- история изменений;
- координация с Quotas и ExternalSystems через контракты, а не прямой доступ к их данным.

### Quotas

- остатки и доступность;
- временные резервы с временем жизни;
- подтверждение и освобождение резервов;
- идемпотентные операции для конкурентного бронирования.

### Accounts

- личный кабинет агента/юридического лица;
- личный кабинет покупателя/физического лица;
- границы агентской и покупательской моделей уточняются до реализации.

### ExternalSystems

- изоляция Core и бизнес-модулей от DTO конкретных поставщиков;
- адаптеры, сопоставление внешних и внутренних идентификаторов;
- журнал и состояния синхронизации;
- повторные и идемпотентные операции обмена.

### Notifications

- подготовка и отправка писем и будущих каналов уведомлений;
- хранение состояния доставки и повторных попыток;
- не определяет расписание отправки самостоятельно.

### Scheduler

Общий планировщик, а не планировщик только для писем. Возможные задания:

- отложенная отправка уведомлений;
- обновление SearchCache и ActualFilters;
- синхронизация внешних систем;
- очистка устаревших резервов;
- периодическое построение отчётов.

### Reporting

- формирование и печать отчётов, ваучеров, договоров и документов;
- использует стабильные контракты и read-модели;
- не становится владельцем исходных Booking/Core-данных.

## Правило создания проекта и host'а

Новый бизнес-модуль получает отдельные Contracts/Application/Domain-проекты, когда у него появляется самостоятельная модель и ответственность. Domain-проект необязателен для чистого orchestration/read-модуля.

Отдельный API/Service-host создаётся, если необходим хотя бы один фактор:

- независимый запуск или масштабирование;
- фоновые задания;
- отдельный жизненный цикл и конфигурация;
- изоляция отказов;
- отдельный внешний HTTP API.

Инфраструктурный проект на каждый модуль не создаётся. Реализации группируются по технологическому provider'у.
