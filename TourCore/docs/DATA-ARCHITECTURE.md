# Архитектура данных TourCore

## Основные принципы

1. У каждой группы данных есть один логический владелец.
2. Разделение бизнес-модулей и разделение баз — связанные, но не идентичные решения.
3. Между независимыми базами не используются физические внешние ключи и межбазовые JOIN.
4. Кеш, индекс, актуальные фильтры и отчётная read-модель являются производными данными и должны восстанавливаться из источников истины.
5. SQL Server и PostgreSQL — две технологические реализации одной логической модели там, где требуется Legacy/Modern совместимость.

## Планируемые источники истины

| Логическая база | Владелец | Примеры данных |
|---|---|---|
| `CoreDb` | Core | страны, города, отели, базовые гостиничные и транспортные справочники |
| `HotelPricesDb` | HotelPricing | контракты, периоды цен, размещения, доплаты и скидки |
| `AviaPricesDb` | AviaPricing | тарифы, сборы, ценовые периоды, классы стоимости |
| `OtherPricesDb` | OtherPricing | трансферы, автобус/ж/д, страховки, визы, экскурсии и прочие услуги |
| `BookingDb` | Booking | заявки, туристы, состав тура, состояния и история |
| `QuotasDb` | Quotas | остатки, временные резервы, подтверждения и освобождения |
| `AccountsDb` | Accounts | агенты, юридические лица, покупатели и профили |
| `ExternalSystemsDb` | ExternalSystems | внешние модели, mappings идентификаторов и журнал синхронизации |
| `NotificationsDb` | Notifications | сообщения, состояния доставки и повторные попытки |
| `SchedulerDb` | Scheduler | задания, расписания, блокировки и история выполнения |

Фактические имена и необходимость отдельной физической базы подтверждаются при проектировании соответствующего модуля.

## Производные технические хранилища

```text
SearchCache / SearchIndex
ActualFilters snapshot
Reporting read models
технические очереди и outbox
```

Search не планируется как владелец транзакционной базы. Его целевой источник — опубликованный SearchCache/SearchIndex. Потеря поискового хранилища не должна приводить к потере бизнес-данных.

Физической реализацией производного хранилища могут быть Redis, память процесса, файлы snapshot, key-value хранилище или PostgreSQL. Выбор технологии не должен проникать в Search Application.

## DbContext и migrations

Инфраструктура общая по provider'у:

```text
TourCore.Infrastructure.SqlServer
├── Core
├── Search
├── HotelPricing
├── Booking
└── Quotas

TourCore.Infrastructure.Postgres
├── Core
├── Search
├── HotelPricing
├── Booking
└── Quotas
```

Но каждый источник истины получает собственный `DbContext`, connection string и набор migrations:

```text
CoreDbContext
HotelPricesDbContext
AviaPricesDbContext
OtherPricesDbContext
BookingDbContext
QuotasDbContext
ExternalSystemsDbContext
```

Host подключает только нужные регистрации. Метод `AddAllInfrastructure()` запрещён как архитектурный шаблон; используются явные регистрации вида `AddPostgresCoreInfrastructure()` и `AddSqlServerBookingInfrastructure()`.

## Ссылки между базами

Идентификатор из другой базы является логической ссылкой, но не внешним ключом. Например, `HotelPricesDb.HotelId` указывает на Core, но не создаёт FK на `CoreDb.Hotels`.

Необходимо различать:

- внутренний идентификатор владельца;
- стабильный бизнес-код;
- внешний идентификатор поставщика;
- код внешней системы.

Глобальная стратегия идентификаторов будет утверждена до реализации Pricing/Booking/ExternalSystems. Нельзя предполагать, что числовой `Id` глобально уникален во всех базах.

## Booking и Quotas

Между `BookingDb` и `QuotasDb` нет общей ACID-транзакции. Целевой процесс:

```text
Booking создаёт черновик
  -> Quotas создаёт временный резерв
  -> ExternalSystems подтверждает услуги
  -> Booking фиксирует подтверждение
  -> Quotas подтверждает использование резерва
```

При ошибке выполняются компенсационные действия и освобождение резерва. До реализации необходимо определить:

- идентификаторы и идемпотентность операций;
- время жизни резерва;
- повторную обработку;
- outbox/inbox;
- состояния частичного подтверждения;
- компенсационные сценарии.

## SearchCache и ActualFilters

Целевая цепочка:

```text
CoreDb + PricesDb + QuotasDb
            -> SearchCache Service
            -> versioned snapshot
            -> Search API
```

SearchCache строит и публикует данные. Search API только читает опубликованную версию. ActualFilters использует совместимую версию исходного snapshot либо собственную производную проекцию.

Необходимо предусмотреть:

- номер версии snapshot;
- время построения и актуальности;
- атомарное переключение версий;
- полный и частичный rebuild;
- поведение при недоступности новой версии;
- наблюдаемость отставания кеша от источников.
