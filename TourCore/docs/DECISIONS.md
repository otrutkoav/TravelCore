# Архитектурные решения TourCore

Документ фиксирует текущее состояние решений. Это не неизменяемый стандарт: изменение допускается осознанно, с обновлением причин и последствий.

## Принято

### Core является предметным фундаментом

`TourCore.Domain`, `TourCore.Contracts` и `TourCore.Application` образуют Core. В него входят базовые туристические сущности и сценарии. Admin API управляет Core и не является отдельным предметным ядром.

Следствие: Core не ссылается на Search и будущие бизнес-модули. Это частично контролируется `Directory.Build.targets`.

### Бизнес-модули физически отделяются от Core

Search оформлен как `TourCore.Search.Contracts` и `TourCore.Search.Application`. Booking, Quotas, Pricing и другие самостоятельные области получают аналогичную модульную границу при начале реализации.

Причина: compile-time защита от сильной связанности важнее экономии нескольких проектов при ожидаемом масштабе системы.

### Infrastructure общая по технологическому provider'у

Сохраняются общие проекты:

```text
TourCore.Infrastructure.SqlServer
TourCore.Infrastructure.Postgres
TourCore.Infrastructure
```

Отдельный инфраструктурный проект для каждого модуля не создаётся. Внутри provider'а модули разделяются каталогами, namespace, DbContext, migrations и явными DI-регистрациями.

### API и фоновые службы разделены по ответственности

Admin, Search, Booking, Quotas и другие публичные контуры получают отдельные host'ы. SearchCache, Notifications и Scheduler предполагаются отдельными Service-host'ами.

### Legacy и Modern используют одну бизнес-логику

```text
.NET Framework 4.8 + EF6 + SQL Server
современный .NET + EF Core + PostgreSQL
```

Различаются host и инфраструктурный адаптер. Contracts/Application/Domain одного модуля не дублируются между технологическими реализациями.

### API версионируется в маршруте

Основной контракт использует `/api/v1/...`. Несовместимое изменение получает новую версию; поведение v1 не меняется молча.

### Единый формат ошибок

Legacy и Modern host'ы используют общий контракт API-ошибки и единое отображение Application/Domain-исключений в HTTP-ответы.

### Структура специализированных услуг принадлежит туру

Группы и элементы авиационной услуги и проживания являются дочерними данными `TourService`. Их изменение выполняется через Application-сценарий полной атомарной замены и увеличивает `TourService.Revision` и `Tour.Revision`.

`TourService.ServiceTypeId` является неизменяемым после создания услуги. Замена
вида услуги выполняется удалением старой и созданием новой, поэтому у одной
услуги не может одновременно остаться специализированная структура разных видов.

Для проживания множественные города, продолжительности и разрешённые отели хранятся в нормализованных дочерних таблицах. Справочные `CountryId`, `CityId` и `HotelId` не имеют внешних ключей: их согласованность проверяется по справочному снимку, а таблицы тура остаются независимыми от физического расположения справочников.

Удаление `TourService` каскадно удаляет её специализированную внутреннюю структуру,
но никогда не удаляет справочные сущности. Удаление родительской услуги при
наличии дочерних `TourService` запрещено. После операции порядок оставшихся услуг
уплотняется, а изменения состава фиксируются ревизиями в одной транзакции.

Автобусный переезд моделируется одной конфигурацией `TourBusTransfer` на услугу,
без групп и участков. Множественные допустимые страны, города, переезды, места
посадки и транспорт хранятся в типизированных дочерних таблицах. FK существуют
только внутри агрегата тура; справочные идентификаторы не имеют внешних FK.

Modern и Legacy host'ы публикуют один контракт автобусного переезда и вызывают
одни Application-обработчики. Отдельные Domain, Contracts или Application для
технологических реализаций не создаются. PostgreSQL/EF Core и SQL Server/EF6
обязаны сохранять одинаковые инварианты, уникальность и каскадное владение.

Железнодорожный переезд использует такую же границу агрегата: одна конфигурация
на услугу, типизированные дочерние наборы и отсутствие внешних FK. В первую
версию включены направление, RailwayTransfers, транспорт и интервалы времени;
ценовой пакет, поставщик и цены отложены до проектирования ценового контура.

Контракт железнодорожной услуги одинаков для Modern и Legacy host'ов. Обе ORM
сохраняют одинаковые обязательные наборы, уникальные индексы, временные поля и
каскадное владение. Отличия схемы допустимы только в типах, обусловленных СУБД,
например `time without time zone` в PostgreSQL и `time` в SQL Server.

### Секреты не хранятся в репозитории

Локальная строка PostgreSQL хранится в .NET User Secrets. Пароли и окруженческие строки подключения не добавляются в tracked-конфигурацию.

## Временные реализации

### Текущий поиск — пробный вертикальный срез

`Ef6TourSearchDataSource`, `SearchReadDbContext` и `TourSearchSql` проверяют API, валидацию и первую модель формирования кандидатов. Они не считаются целевым механизмом высоконагруженного поиска.

Граница `ITourSearchDataSource` должна сохраниться. При появлении SearchCache текущий SQL-источник заменяется адаптером кеша без обязательного изменения HTTP-контракта и UI.

### PostgreSQL dev-данные

`Seed-PostgresDevelopment.ps1` создаёт независимый тестовый набор через Modern Admin API. Он предназначен только для локальной разработки, не является production seed и не копирует SQL Server.

### No-cache реализация Modern Admin

До проектирования кешей Modern Admin использует pass-through/no-op реализации каталоговых cache-интерфейсов. Это временная инфраструктурная композиция, а не целевая кеш-архитектура.

### Универсальное хранение ограничений авиаперелёта

Допустимые страны, города, авиакомпании, рейсы, аэропорты и тарифы сейчас хранятся в общей таблице `TourFlightRestrictions` как сочетание `TourFlightId`, `Type` и `ReferenceId`.

Такое представление выбрано для пакетной загрузки и простого расширения. Это внутренняя деталь persistence: API продолжает использовать именованные массивы идентификаторов. После появления реальных профилей нагрузки решение может быть пересмотрено в пользу типизированных таблиц без изменения публичного контракта.

`ReferenceId` не имеет внешнего ключа на справочники. Проверка внешней согласованности выполняется прикладной логикой по доступному справочному снимку или кешу.

## Отложено осознанно

- полноценные unit/integration/API автотесты — после стабилизации модулей и PostgreSQL реализации;
- производительность поиска — после проектирования SearchCache и ActualFilters;
- централизованное логирование и трассировка;
- авторизация и разграничение доступа;
- внешний deployment и production hardening;
- выбор физической технологии кеша;
- окончательная стратегия идентификаторов между базами;
- orchestration/saga для Booking и Quotas;
- outbox/inbox и транспорт событий;
- точные границы Accounts для юридических и физических лиц.

Отложенные пункты нельзя считать отменёнными. Перед началом соответствующего модуля решение должно быть принято и добавлено в документацию.

## Критерии пересмотра структуры

Решение о выделении отдельного репозитория, NuGet-пакета или инфраструктурного проекта принимается только при конкретной причине:

- отдельная команда и независимый релизный цикл;
- несовместимые runtime/зависимости;
- необходимость отдельного deployment ownership;
- неприемлемое время сборки;
- невозможность поддерживать границу текущими project references и architecture tests.

Новый модуль не помещается в Core только ради удобства. Сначала проверяется вопрос: имеет ли сущность смысл как фундамент TourCore или принадлежит самостоятельной бизнес-области.
